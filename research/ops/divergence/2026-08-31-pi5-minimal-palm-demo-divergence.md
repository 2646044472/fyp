# Divergence Packet: 2026-08-31 Raspberry Pi 5 minimal palm demo

## Decision investigated

Given a Raspberry Pi 5 (8 GB), 64 GB card, official camera module, and the three supplied archives under `code/data/`, determine which *minimal palm demo* can be deployed now and which distinct research directions it can honestly support later. The decision is deliberately narrower than choosing a thesis: a working RGB camera-to-template demonstration is required engineering evidence, but it is not itself a new recognition method, liveness claim, or cross-device result.

## Search boundary

## Recent-paper limitation map

- [K] Palm-ID demonstrates that a full contactless palm pipeline can comprise ROI localisation, enhancement, embedding and compact matching, with a mobile deployment. Its reported 18 ms template-extraction and 0.33 ms gallery-search figures run on an AMD EPYC server configuration, so they cannot be presented as Pi 5 timing. The paper is therefore a pipeline decomposition reference, not a deployable Pi artifact.
- [K] PalmRSS already frames device/environment shift as palm recognition single-source domain generalisation. A new model trained on the supplied data to cope with camera mismatch would collide with that task unless it adds a different, predeclared observation/action/endpoint.
- [K] The active P2-CTB direction already constrains the research question to whether a frozen reconstruction baseline transfers from source device/model A to target device/model B above a frozen impostor/FAR reference. Same-device failure or cross-device transfer at FAR is a useful barrier result, not a failed demo.
- [K] Raspberry Pi's current camera documentation specifies the `rpicam-*` applications on Bookworm and Picamera2 for Python. The official manual recommends installing Picamera2 from the OS package manager; it warns that arbitrary pip installs can be incompatible with the installed libcamera Python bindings. This supports a stable capture layer, not a palm model's ARM compatibility.
- [K] ONNX Runtime publishes an Arm CPU installation route and a Raspberry Pi computer-vision tutorial. It supports selecting ONNX Runtime as a candidate inference runtime only after a lawful, frozen model actually loads on the target board; it does not supply a palm model, ROI detector, threshold, or Pi 5 benchmark.

## Top two formalizations

### D0: deterministic local 1:1 deployment gate

- **[D]** A consented enrolment consists of a locally assigned pseudonymous identifier, one or more RGB capture frames, camera/ROI settings and a template. A probe is an independently captured frame that claims one enrolled identifier. Public archive images, if used, enter a separate offline manifest.
- **[A]** The Pi executes `capture -> palm/ROI validity -> normalise -> feature/template -> cosine or L2 score -> match / no-match / reacquire`, storing a timestamp, model/descriptor hash, score, threshold and decision. Raw frames are not needed for the normal operation log.
- **[T]** Demonstration readiness, measured by end-to-end latency distribution, template-store round trip, valid-ROI/retry rate and deterministic replay scores. It is not an FAR/FRR or spoof-security study.
- **Observable outcome:** the same stored test image has identical template and score within a frozen software build; capture failures/retries and timing are observable on the Pi.
- **Counterexample:** same input produces different templates/scores, the camera loop blocks, or no usable ROI can be captured at the stated geometry.
- **Negative-result value:** pinpoints whether capture, ROI, runtime, storage or matching prevents deployment before pursuing any biometric claim.

### P2-CTB: transfer boundary on a low-cost target matcher

- **[D]** A template `e_A=f_A(x_A)` is leaked from a source image/device/model cell A. The experiment has a frozen target matcher B and a public or consented, authorised offline probe set. It excludes a live service, production credentials and uncontrolled physical attacks.
- **[A]** Run a fixed reconstruction/inversion baseline that maps `e_A` to a candidate representation/image. Evaluate target acceptance on B under a threshold frozen from B's disjoint development impostor set; report same-device, cross-model and cross-sensor/model cells separately.
- **[T]** `ASR_B(tau_B)` against the matched B impostor FAR at `tau_B`, after validating that the baseline can work in its same-device cell.
- **Observable outcome:** binomial confidence interval for attack acceptance and the difference from B's frozen FAR, plus all source/target cell identifiers.
- **Counterexample:** a candidate matches its source embedding but does not exceed the target's impostor FAR; or the result changes only because a threshold was tuned after observing attack data.
- **Negative-result value:** bounds transfer for this low-cost capture/matcher configuration and prevents a stronger claim about universal biometric inversion.

## Decision

Deploy D0 first: it is the only candidate fully supported by the hardware already confirmed, and it is an engineering baseline rather than a research contribution. D1 is the appropriate next gate if consent/data permission is available. P2-CTB remains the active conditional research direction and should start with an offline same-device sanity pilot, not with a claim that the first Pi demo establishes cross-device attack transfer. D3 is retained only as a transparent capture/retry control. D4 is unavailable with the stated RGB camera.
