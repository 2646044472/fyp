# Validation Audit: 2026-09-17 palm-payment MVP and post-MVP research boundary

## Decision investigated

I audited the post-reset staged plan in `docs/superpowers/plans/09-13-palm-payment-phase1.md` against the user-confirmed roadmap in `minutes/09-13-palm-payment-roadmap-update.md`. The decision under test is whether one plan can defensibly carry the project from a Raspberry Pi 5 Phase 1 palm-payment-like MVP into later NIR/fusion, physical-attack and PAD research.

The audit also checked the current implementation artifacts (`code/palm_demo/README.md`, `BASELINES.md`, `SOURCE_MANIFEST.md`, `palm_demo.py`, `debug_ui.py`), the newest 2026-09-13 divergence and validation packets, and the newer 2026-09-17 divergence packet. Search and source checking were performed on 2026-09-17. The scope is local, consented, simulated-payment research only: no financial authorization, production security, PAD, liveness, demographic, cross-device or population-performance claim is assumed.

## Claim under test

The charitable claim is:

> A modular Pi 5 palm-payment MVP, followed by controlled NoIR/NIR capture, simple or learned VIS/NIR fusion, and later physical presentation-attack/PAD evaluation, provides a coherent and potentially defensible FYP path.

The claim separates into three materially different propositions:

1. **Phase 1 engineering proposition [C]:** the present fixed-stand 1:1 Fast-CC demo can be refactored into a local 1:N, unknown-user, simulated-ledger workflow with automatic ROI, explicit retry, deterministic deletion and a payment-like UI by December 2026.
2. **Post-MVP research proposition [C]:** a NoIR-plus-IR path can be named palm-vein and support a novel fusion/acquisition contribution.
3. **Security proposition [C]:** physical print/replay attacks followed by a lightweight PAD component can form a later research contribution on the same platform.

My result is mixed: [K] the MVP is a reasonable engineering target, but [GAP] it is not yet implementation-ready or data/ethics-cleared; [KILL] generic NIR/fusion, quality-aware routing, palmprint PAD and “payment-like edge deployment” contributions collide with direct work; [PIVOT] only a tightly bounded, independently labelled, held-out action or negative-result study could reopen a thesis claim after the MVP and hardware gates.

## Assumption and identification audit

### Phase 1 observation/action boundary

[K] The current artifact is a fixed-stand 1:1 verifier. `palm_demo.py` uses a fixed fractional crop, Fast-CC, a contrast gate, five enrollment samples and a provisional threshold of `0.28`; `debug_ui.py` asks for a user identifier and exposes enrollment/verification routes. [K] The plan's target behavior is materially different: a payment user must not enter an identifier; the system must search a gallery, decide `MATCH / UNKNOWN / RETRY`, and only then call a simulated ledger.

[GAP] That 1:1-to-1:N and debug-UI-to-payment-UI transition is not a small configuration change. The current code stores a threshold in each user's metadata and allows a per-run verification override, while the plan requires one system-level frozen policy. The current code has no gallery, payment SQLite schema, transaction idempotency, checkout workflow, automatic ROI, account lifecycle, deterministic deletion across template and ledger data, or payment UI. The plan is therefore an implementation proposal, not evidence that the MVP already runs.

[K] A local simulation makes the payment decision identifiable as a software state transition: if identity is accepted, a request ID is new, and balance is sufficient, the ledger can deterministically deduct once. [C] It does not make the identity trustworthy in a security sense. The same score can be a useful demo decision and an unsafe payment authorization; the roadmap must keep those claims separate.

### 1:N threshold, unknown users and sample size

[K] `1:N` is an open-set decision, not merely “pick the best user.” The plan correctly requires a frozen threshold and optional margin; however, the acceptance test of two enrolled users plus one unenrolled person is a bring-up test, not a performance study. [K] Genuine/impostor score construction, fixed operating points and uncertainty reporting are standard biometric evaluation objects under ISO/IEC 19795-1:2021. [K] Palm-ID reports closed/open-set endpoints and time-separated data at substantially larger scale; the 2019 mobile-platform work used 200 subjects and two sessions.

[GAP] The plan does not fix a target operating point, confidence interval width, number of independent hands, session count, or impostor sampling design. A large number of pairwise comparisons among three to five people would not support a low FMR claim. [KILL] Any thesis or security language based on the Phase 1 acceptance cases, the 20 x 10 archive-derived smoke subset, or frame counts would be invalid. [E] The local source manifest itself labels the subset development-only and leaves the archive agreements unresolved.

### Automatic ROI and ring/environment claims

[K] The plan's first automatic ROI is background subtraction, largest connected component, geometry/orientation normalization and a central palm crop, with explicit retry on ambiguity. This is a sensible constrained engineering baseline. [K] Aykut & Ekinci (2015) already target contactless ROI extraction under position/orientation and clutter; Chai et al. (2025) explicitly study open-environment ROI without finger-valley points; Palm-ID already uses learned keypoints and quality rejection. [K] A synthetic crop-offset/rotation/scale sweep is also an established stress test in current ROI work.

[GAP] The plan does not yet define independent physical labels for hand clipping, ring type/location, pose, background, exposure or illumination. If the automatic ROI creates the label “ROI succeeded,” then evaluates itself using that same output, the claimed cause is circular. If ring, pose, lighting and background are collected together, no one factor is identifiable. [PIVOT] Keep ring/environment as a blocked physical-factor measurement and action study only; do not promote a new ROI network or call a lower EER a new contribution.

### NoIR, NIR and palm-vein identifiability

[K] Raspberry Pi identifies NoIR variants as cameras without an IR-cut filter and documents different AWB tuning; Camera Module 3 specifications distinguish standard and NoIR variants. [K] The current confirmed inventory is only a Raspberry Pi and Camera NoIR v2; the exact camera revision, sensor response and any visible-light camera remain [GAP]. A profile called `rgb` cannot silently mean a standard RGB path when only NoIR hardware has been verified.

[K] Direct palm-vein systems specify NIR-sensitive cameras, wavelength, visible-light rejection, illumination geometry and controlled placement. Wu et al. use an NIR CMOS camera, 850 nm LED array and a light-controlled capture box; Piciucco et al. use an 850 nm source and an 825 nm cut-on filter with a docking device. [K] A NoIR camera plus an IR fill light may be a useful alternate illumination path, but it is not by label equivalent to a palm-vein acquisition system or CASIA multispectral data.

[GAP] The roadmap does not yet provide the LED peak wavelength/bandwidth, optical power or irradiance, filter, enclosure, geometry, exposure/gain, sensor response, capture order, safety assessment or a repeatability protocol. Sequential VIS/IR acquisition also changes time, pose and camera state. A vascular-looking enhancement output cannot distinguish subcutaneous vessels from visible creases, shadows, auto-exposure artifacts or sensor noise without a frozen comparison.

[KILL] “Add 850 nm and fuse RGB with NIR” is not a research boundary. [PIVOT] The only viable later gate is: characterize NoIR+IR separately; establish repeatable signal across people and sessions; run VIS-only and IR-only baselines; then compare fixed equal-score fusion, unimodal fallback, always-two-shot and a predeclared intervention policy at matched capture/latency/energy cost. If those controls dominate or the signal is not repeatable, retain the path as NoIR+IR alternate illumination and stop palm-vein terminology.

### Fusion, missing modality and auxiliary hand features

[K] Fan et al. (2024) perform two-stage palmprint/palm-vein recognition with genuine/impostor/uncertainty routing and adaptive weighted fusion. [K] Pan et al. (2025) explicitly reconstruct missing palmprint/palm-vein modality features. [K] BPFNet addresses bimodal ROI localization/alignment and image fusion, and Yu et al. (IJCB 2025) address early fusion for embedded efficiency. [K] HGAIQA already uses whole-hand geometry, flatness, brightness and sharpness to improve downstream palmprint EER; Bob Zhang is a coauthor, so this is a direct advisor-neighbor check rather than superficial adjacency.

[KILL] Learned fusion, quality-weighted fusion, missing-modality reconstruction, finger-ratio identity fusion and “edge-efficient multimodal recognition” are occupied claims. [GAP] The current plan has no paired lawful Pi VIS/NIR corpus, no independent modality-missing label, no frozen unimodal models, no cross-session identity split and no measured energy instrument. A fixed normalized score sum and best-unimodal fallback are mandatory controls, not optional ablations.

### PAD and physical attacks

[K] ISO/IEC 30107-3:2023 defines PAD performance assessment, result reporting and attack classification for attacks at the biometric capture device; it excludes overall system security and vulnerability assessment. [K] DAPANet (2025) already studies domain-adaptive palmprint anti-spoofing across multiple spoofing domains. [K] GBU-Palm (arXiv v1, 2026-08-14) supplies 21,326 native videos from 105 subjects/210 palms, synchronized RGB-NIR samples, Print/Replay attacks, six environments, identity/attack-lineage-disjoint splits and held-out-environment analysis; it reports that RGB-NIR benefit is architecture-dependent rather than automatic. [K] EchoHand (CCS 2022) demonstrates commodity-device hand authentication with an additional physical sensing channel and explicitly evaluates presentation-attack resistance. [K] Yan et al. (2024) already occupy black-box palm-template reconstruction against palm matchers.

[KILL] A later plan that merely adds printed palms, screen replay, a lightweight classifier and APCER/BPCER numbers would be a standard PAD replication unless the exact attack instruments, capture path, subject-disjoint protocol, unknown-attack split and decision endpoint are made distinct. GBU-Palm also makes generic synchronized RGB/NIR, temporal PAD and cross-environment claims especially collision-prone. A digital ROI injected directly into the matcher is not a physical attack experiment: it bypasses the target camera, optics, ROI acquisition and any PAD path. [GAP] The current plan specifies neither attack materials nor a PAD threat model, presentation protocol, bona-fide/attack sample counts, unknown-PAI test, or independent attack apparatus.

[PIVOT] Physical attack work may remain a later, separately authorized benchmark after the MVP, but it cannot be presented as an automatic consequence of adding NIR or as “payment security.” PAD must be a separate module and claim, with ISO/IEC 30107-3-style reporting and explicit limits.

### Data, ethics and privacy

[GAP] The local manifest records `PalmBigDataBase.zip` and `CASIA-Multi-Spectral-PalmprintV1.rar`, hashes, observed filenames and intended local uses, but not source agreements or publication/training rights. The 20 x 10 derived subset is explicitly smoke-test/development data. X-Palm is a stronger direct protocol neighbor, but its repository requires a signed academic EULA and time-limited access; its compound smartphone factors are not a license to infer a named Pi sensor effect.

[K] Palm images, templates and identity-linked transaction traces are biometric/personal data even when stored locally. [GAP] No ethics approval decision, consent form, target cohort, retention period, deletion verification or access-control plan is present in the supplied roadmap. The camera authorization switch in the current code is a procedural guard, not ethics approval. [KILL] No human capture, public release, training, or security/financial claim should be treated as cleared by the existence of that switch.

[PIVOT] Phase 1 can proceed with deterministic synthetic-image tests and, only after supervisor/institution approval, a minimal consented smoke test. Store pseudonymous IDs, separate templates from simulated accounts, minimize raw-frame retention, log deletion, and make deletion atomic across template, user, account and transaction state. Do not use unresolved archives beyond inventory until terms are recorded.

### Hardware, resource and implementation readiness

[K] Raspberry Pi's current documentation recommends a 27 W USB-C supply for Pi 5, with 5 V/5 A operation and lower peripheral-current limits with a 3 A supply. [K] The camera stack is libcamera/rpicam/Picamera2; NoIR variants can require distinct tuning files, and multiple-camera capture has camera-state/timing caveats. [GAP] The exact Pi model/RAM, supply, cooling, camera revision, cable/mount, visible-light path, IR source/filter, measurement instrument and delivery dates are not all confirmed.

[E] The local README records a verified private USB-C SSH connection and contains a plaintext development credential. I do not reproduce it here. [KILL] Before any Wi-Fi/LAN exposure, remove the credential from documentation and rotate it; this is a concrete security/readiness defect even though it is outside the research claim. [GAP] The current plan's “portable” definition does not yet include a clean-boot reproducibility check, power/cooling envelope, offline dependency lock, camera-index manifest, or recovery procedure.

[E] The current tree contains only the original `palm_demo.py`, `debug_ui.py`, setup scripts and calibration tools; the plan's `models.py`, `camera.py`, `biometric.py`, `templates.py`, `gallery.py`, `payment.py`, `workflow.py`, `palm_payment_ui.py`, `roi.py` and test files are not present in the current artifact listing. [K] That is consistent with the plan being unexecuted. [GAP] No Pi 5 acceptance run, 1:N run, payment transaction, restart persistence, deletion test or automatic-ROI capture log was found in the requested workspace inputs.

## Strongest simple baseline

The decisive baseline is a frozen, cost-inclusive transaction matrix rather than a new recognizer:

1. Current fixed ROI + Fast-CC, with one system-level threshold frozen on development identities/sessions.
2. Same matcher with score-only `MATCH / UNKNOWN` and no quality rule.
3. Fixed guide/manual crop plus deterministic contrast/sharpness/coverage gate.
4. Fixed one-recapture policy, always-two-shot policy and always-abstain policy.
5. Automatic ROI only as a candidate policy beside the fixed guide, never as the sole truth source.
6. For IR: VIS-only, NoIR+IR-only, fixed equal normalized-score sum, best-unimodal fallback and always-recapture.
7. For geometry: matcher score + ROI validity/landmark confidence before any identity-feature concatenation.
8. For PAD: no-PAD recognition baseline, a transparent texture/quality control, and attack/bona-fide presentation protocol with subject- and instrument-disjoint test cells.

Every policy must use the same enrollment and held-out transaction stream, with identity/session clustered uncertainty. Report false match, false non-match, failure-to-acquire, unknown-user rate, retries, p50/p95 transaction time, and only directly measured energy. Charge every extra capture and intervention. If a proposed fusion, ROI, quality, PAD or HCI method does not produce a non-dominated held-out point over these controls, it is unnecessary for the FYP claim.

For Phase 1 implementation, the minimal acceptance baseline is even narrower: deterministic image tests, fixed-crop local 1:1 characterization, then gallery search, then one complete simulated transaction, followed by unknown-user, retry, insufficient-balance, restart and deletion tests. Automatic ROI and the payment-facing UI should not be declared complete until this sequence passes on the Pi.

## Contrarian result

The roadmap is coherent as project management and overstates what its later research sequence buys. “Build first, add IR, then fuse, then attack, then PAD” is a natural engineering order, but each later noun is already a mature research family. The order does not create a new observation model, action, guarantee or endpoint.

[KILL] The current post-reset plan cannot be promoted as a palm-recognition, NIR-fusion, PAD or payment-security thesis merely because it has a Raspberry Pi, a simulated balance, a second camera path, a better EER, a lower retry rate, or a later print demo. [KILL] Phase 1 itself is not a security system; its identity-to-ledger path is a local software demonstration whose main risks are stale thresholds, unknown-user calibration, incomplete deletion and implementation bugs.

[PIVOT] The surviving scientific object is a single gated question after the MVP: for a named, fixed apparatus and named physical cells, does an independently observed quality/intervention signal change the held-out decision frontier of `decide / one guided recapture / abstain` at matched false-match, latency and measured-energy cost? A null result is valuable: it can show that fixed recapture, score-only gating, equal fusion or abstention dominates and that the low-cost apparatus does not justify a claimed palm-vein/PAD contribution.

## Decision

Keep Phase 1 only as a gated, local, simulated-payment engineering milestone. Before implementation expands, fix the current credential exposure, clear data/ethics permissions, verify the exact Pi/camera/power/mount inventory, replace per-user provisional thresholds with a single frozen 1:N policy, and implement the missing gallery/ledger/workflow/UI/ROI/deletion/tests in the stated order. Treat the 2+1 acceptance cases and 20 x 10 subset as bring-up evidence, not biometric performance or security evidence.

Do not promote NIR/fusion, auxiliary geometry, PAD, print/replay attacks, palm-vein wording, or payment-security language from the roadmap alone. After the MVP, choose at most one research gate: a preregistered, identity/session-blocked physical-factor or IR-intervention study with independent labels, explicit `decide / recapture / abstain` action, matched time/energy cost and transparent fixed baselines. A null or baseline-dominated result should close the branch rather than trigger model shopping.
